# Research: シミュレーショングラフの操作性改善

入力：[spec.md](spec.md)、正本 `docs/simulator/index.md` v1.3 6.3、基準コミット `ef3435f` の `LifePlan/wwwroot/js/life-plan-chart.js`・`LifePlan/wwwroot/css/life-plan.css`・`LifePlan/Views/LifePlan/Index.cshtml`。

Technical Context に NEEDS CLARIFICATION はない。以下は設計上の判断の記録。

## R1. ツールチップを Canvas に描くか、HTML 要素で重ねるか

- **Decision**: HTML 要素（`div`）をグラフ枠（`.life-plan-chart__canvas-wrap`）内に絶対配置で重ねる。折れ線・縦線・マーカーは従来どおり Canvas に描く。
- **Rationale**:
  - カーソルをツールチップ上に移しても消えない（WCAG 2.2 1.4.13 の hoverable）ためには、ツールチップが自分でポインターを受け取る必要がある。Canvas 内の描画ではできない。
  - 文字の折り返し、色トークン、フォントを CSS で扱え、数値表示欄とスタイルを共有できる。
  - 金額の文字情報が DOM に残るため、ブラウザの拡大や文字の読み取りが効く。
- **Alternatives considered**:
  - Canvas に描画：外部ライブラリなしで簡単だが、hoverable を満たせず、文字の拡大・選択もできない。
  - グラフ下部の数値表示欄をホバー中だけ切り替える：Clarifications Q2 で不採用（固定表示と一時表示が混ざる）。

## R2. ホバーの検出と終了

- **Decision**:
  - `pointermove` で `pointerType === 'mouse'` かつボタンを押していない（`buttons === 0`）ときだけ、ホバー年度を更新する。
  - ホバー領域は「グラフ枠（`.life-plan-chart__canvas-wrap`）とその中のツールチップ」とし、枠の `pointerleave` で終了する。ツールチップは枠の中にあるため、グラフからツールチップへ移っても終了しない。
  - Esc キー（`document` の `keydown`）で終了する。その後は、ホバー年度が変わるか、カーソルが一度枠から出て戻るまで再表示しない。
  - マウスのボタンを押している間（クリック・ドラッグ）はツールチップを出さない。離した後、次の `pointermove` で再表示する。
  - タッチ・ペンでは `pointerType` で除外し、ツールチップを出さない（FR-007、Assumptions）。
- **Rationale**: 入力方法で分ける方針（Clarifications Q1）を、デバイス判定ではなくイベントごとの `pointerType` で実現できる。タッチとマウスの両方を使える端末でも、操作ごとに正しく振る舞う。
- **Alternatives considered**:
  - `mouseenter`/`mouseleave`：タッチ端末で互換マウスイベントが発生し、タップ後にツールチップが残る恐れがある。
  - `matchMedia('(hover: hover)')` で一括判定：両方を使える端末で、タッチ操作時にもホバー処理が走る。

## R3. ツールチップの配置

> 2026-10-12 改訂（実装時の確認とレビューによる）：初版の「プロット領域の上端に固定」では、カーソルを横に動かすとツールチップに乗り、ホバーの更新とクリックが止まった。そのため、下記のとおり変更した。

- **Decision**:
  - 「カーソルの通り道」を、ホバー年度になる横の範囲（縦線から年度間隔の半分ずつ）の、カーソルの高さの帯とする。ツールチップは、この帯と重ならない位置に置く。
  - 次の順に候補を試し、帯と重ならない最初の候補を選ぶ。どの候補もグラフ枠内に収める。
    1. カーソルと反対側の半分（カーソルが上半分なら下端、下半分なら上端）に置き、縦線のすぐ横（右、収まらなければ左）に置く
    2. 同じく反対側の半分で、縦線の逆側に置く
    3. カーソルと同じ半分で、横の範囲の外（右、収まらなければ左）に置く
    4. 同じく同じ半分で、横の範囲の逆側の外に置く
  - 1・2 の「すぐ横」の間隔は、年度間隔の4分の1（最大12px、最小1px）とする。ツールチップの端が横の範囲に入るので、同じ年度のまま縦に動けばツールチップへ移れる。
  - 3・4 を使う場合と、どの候補でも帯と重なる場合は、ツールチップをポインター操作の対象から外す（`life-plan-chart__tooltip--passthrough`、`pointer-events: none`）。主に、狭い表示でツールチップがプロット領域の半分より高いときに起きる。
    - 3・4 は帯の外にあり、もともと縦の移動では届かない。一方、カーソルと同じ高さにあるので、速いマウス移動ではイベントの間隔（数〜十数px）で余白を飛び越えて乗りうる（2回目のレビューの指摘）。
    - 透過させても、ホバーの更新とクリックは止まらない。
  - 位置は、ホバー年度が変わったときだけ決め直す。
  - ツールチップの行の高さと行間を詰め、上下で避けやすくする（4項目で約125px）。
- **Rationale**:
  - 横に動かしてもツールチップに乗らず、ホバーの更新とクリックが止まらない。
  - 同じ年度のまま縦に動けば、ツールチップに乗れる（WCAG 1.4.13 の hoverable）。
  - ホバー中の縦線とマーカーは、ツールチップの端からわずかに外れる位置に残る（FR-005）。
- **検証（ハーネス、`sweep2`）**：
  - 条件：幅500pxと1280px、年数1・2・5・10・15・40・85年、7桁の金額あり・なし。
  - なぞり方：行ごとにグラフ外へ出してから、21の高さで左右両方向に横になぞる。最前面の要素にイベントを送るので、ツールチップの上ではグラフにイベントが届かない。
  - 結果（最終のロジックで再計測）：ツールチップに遮られた回数、ホバー年度の更新漏れ、クリックが届かない位置は、すべて0。
    - 透過になったのは、カーソルと同じ高さに置いた場合だけ。幅500px（年数10・15・40年）では2412回で、すべて透過。1280px では0回で、常に反対側の半分に置かれた。
    - グラフ外から入ってすぐの171点では、透過は0回。
  - 縦に動いてツールチップに乗れた割合：ほぼすべての条件で 20/20。85年分で幅が狭い場合だけ 8/20 で、年度の横の範囲が約±2pxと狭いため。
  - 速いマウス移動（`step=8/16/24`）：幅500px・1280px、年数10・15・40年、7桁の金額あり、プロット領域の中央±40pxの高さで左右に動かした。
    - ツールチップに遮られた回数、更新漏れ、クリックが届かない位置は、全条件で0。
    - 幅500pxでは、カーソルと同じ高さにツールチップを置く候補（3・4）が実際に使われ（270〜788回）、すべて透過になっていた。
    - 1280px では候補3・4は使われず、常に反対側の半分に置かれた（ツールチップへ乗れる）。
- **Alternatives considered**:
  - ツールチップを常に `pointer-events: none` にする：横移動の妨げはなくなるが、カーソルをツールチップへ移せず、1.4.13 の hoverable を満たさない。
  - カーソルに追従させる：マーカーを覆いやすく、細かい揺れで位置が動いて読みにくい。
- **Alternatives considered**: カーソル追従（マウス座標の近く）は、ツールチップがマーカーを覆いやすく、細かい揺れで位置が動いて読みにくい。

## R3a. ツールチップのクリックによる固定（実装後の追加修正）

- **Decision**: ツールチップの `click`（左ボタン）で、表示中のホバー年度を固定する。一時表示を終了している（Esc など）ときと、ツールチップ内の文字を選択しているとき（金額をドラッグで選んでコピーする操作。レビューでの懸念による）は何もしない。透過中のツールチップは、クリックがそのままグラフに届く。グラフ上でのカーソル位置の年度は表示中の年度と同じなので、結果は同じになる。ツールチップにはカーソル `pointer` を付ける。
- **Rationale**:
  - ツールチップはカーソルが乗れる（1.4.13）ため、ツールチップの上ではクリックがグラフに届かず、固定できなかった。ユーザー確認で A案を採用した。
  - `role="tooltip"` の要素は本来操作対象ではないが、このクリックはマウス向けの補助にとどめ、フォーカスは持たせない。キーボード・支援技術での同じ操作は、年度選択欄で行える。
- **Alternatives considered**: ツールチップを常に透過させる案は、1.4.13 の hoverable を満たさなくなるため不採用（R3）。

## R4. 一時表示と固定表示の区別

- **Decision**:
  - 固定表示（既存を維持）：グレーの破線の縦線と、白抜きのマーカー。グラフ下部の数値表示欄。
  - 一時表示：グレーの実線の細い縦線と、系列色で塗りつぶした小さめのマーカー。ツールチップの見出しに「カーソル位置」の文言を付ける。
  - 数値表示欄の見出しには「固定中」の文言を付ける。
  - 固定年度とホバー年度が同じときは、両方を描く（固定の表示を優先して上に重ねる）。
- **Rationale**: 色以外に、線種（破線／実線）、マーカーの形（白抜き／塗り）、文言で区別できる（FR-004、WCAG 1.4.1）。既存の固定表示の見た目は変えない（spec「維持する機能」）。
- **Alternatives considered**: ホバー線を薄い色だけで区別する案は、色だけに頼るため不採用。

## R5. 操作案内の出し分け

- **Decision**:
  - 案内文はビューの HTML に2種類（PC向け、タッチ向け）を置き、CSS のメディアクエリ `(any-hover: hover) and (any-pointer: fine)` で出し分ける。条件に合うとPC向け、合わないとタッチ向けを表示する。
  - 文言は次のとおり。
    - PC向け：「カーソルを合わせて金額を確認・クリックで年度を固定（←/→キーでも年度を選択できます）」
    - タッチ向け：「グラフをタップして年度を選択」
  - 配置は、表示項目チェックボックスとグラフ枠の間。小さい文字（`--ui-font-size-small`）、補足色（`--ui-color-muted`）。
  - グラフを表示できない環境では、案内文を出さない。案内文は `hidden` で出力し、グラフの初期化に成功したときに JavaScript が表示する。
- **Rationale**:
  - `any-hover`/`any-pointer` を使うと、タッチとマウスの両方を使える端末ではPC向けになる（Clarifications Q1）。
  - 表示の切り替えに JavaScript の判定を使わないので、ちらつきがない。
  - 画面文言をビューに置くのは既存の慣例どおり。憲章 原則 V の文言の正本規定は入力検証メッセージが対象で、案内文は対象外。
- **Alternatives considered**:
  - 画面幅で出し分ける案は、Clarifications Q1 で不採用。
  - JavaScript で文言を生成する案は、文言がビューと JavaScript に分散するため不採用。

## R6. 支援技術とキーボードによる年度の選択（FR-019〜022）

> 2026-10-12 改訂：初版の「Canvas を `role="slider"` にする」案は、レビュー（ユーザー確認）で未選択状態との整合とスマートフォンの読み上げソフトでの操作に懸念が示されたため、検討し直して下記に変更した。

> **2026-10-12 再改訂（年度選択欄の表示仕様の変更）**
>
> ユーザーの指示で、年度選択欄を「キーボードでフォーカスしたときだけ表示（`visually-hidden-focusable`）」から「PC・スマートフォンとも常に表示」に変更した。
>
> - 理由：スマートフォンでは、狭いグラフでタップして狙った年度を選びにくい。一覧から確実に選べるようにする。
> - 実装
>   - 包む要素から `visually-hidden-focusable` を外した。
>   - CSS は `.life-plan-chart__year-select` を常に flex で表示する。選択欄は `flex: 1 1 10rem`、最大 14rem、`min-width: 0` で伸縮し、狭い幅では折り返す。
>   - JS（選択肢の生成、相互同期、←/→/Home/End）は変更なし。
> - 以下の Decision のうち、「`visually-hidden-focusable` で通常は表示しない」「マウス・タッチの利用者から見た画面は変わらない」「フォーカスした間だけ数値表示欄が下がる」と、Alternatives の「年度選択欄を常に表示する案は不採用」は、この再改訂で置き換えた。
> - slider 案を不採用にした評価と、標準の `select` を使う判断は、そのまま有効。

### slider 案の評価

| 観点 | 結果 |
| --- | --- |
| 未選択状態との整合 | ✗ WAI-ARIA 1.2 では、`slider` の `aria-valuenow` は必須。未選択時にも何かの年度を値として持たせる必要がある。`aria-valuetext` を「年度未選択」にしても、`aria-valuenow`（例：最初の年度）を読む支援技術があり、状態が食い違って伝わる |
| 年度と金額の理解 | △ 年度は値として伝わるが、金額は別の領域（数値表示欄）に頼る |
| Canvas に頼らない取得 | ○ 金額は数値表示欄の文字情報で取得できる |
| スマートフォンの読み上げソフト | ✗ VoiceOver・TalkBack の上下スワイプによる調整は、独自の ARIA スライダーでは環境によって動作が異なる。Canvas のキー操作（keydown）に届く保証がない。また、読み上げ中のダブルタップは要素の中央をタップしたことになり、意図しない年度（中央の年度）を固定してしまう |

同じ理由で `role="spinbutton"`（ARIA 1.2 では値なしを許す）も、スマートフォンの読み上げソフトでの操作に保証がないため採用しない。

### Decision

年度の選択を、標準の `select` 要素（年度選択欄）で支援技術とキーボードに提供する。Canvas はマウス・タッチ専用の図とする。

- **年度選択欄**
  - グラフ枠と数値表示欄の間に、ラベル「表示する年度」付きの `select` を置く。
  - 包む要素に Bootstrap の `visually-hidden-focusable` を付け、通常は表示せず、キーボードでフォーカスしたときだけ表示する。マウス・タッチの利用者から見た画面は変わらない（FR-024）。
  - 選択肢の先頭は「年度を選択」（`value=""`、`disabled`）とし、初期状態で選ぶ。続けて各年度「2026年」…を並べる。
    - 未選択状態は既存どおり。一度選んだ後に未選択へ戻す操作は、ポインター操作と同じく設けない。
  - 年度選択欄と固定中の年度は、どちらから変えても同期する。
    - 年度選択欄を変えると、その年度を固定する。
    - クリック・タップ・ドラッグで固定すると、年度選択欄の値を更新する。
  - キー操作：↑/↓/Home/End と、文字入力による項目移動は、ブラウザ標準のとおり。←/→ も、OS によらず前後の年度に移るよう補う。既存の Canvas の ←/→/Home/End と同じ割り当てになり、案内文「←/→キーでも年度を選択できます」とも一致する。
  - スマートフォンの読み上げソフトでは、標準のピッカー（iOS）や一覧（Android）で選べる。
- **Canvas**
  - `role="img"` を維持し、`tabindex` を外してフォーカス対象から外す。
  - `aria-label` は「収入、支出、貯蓄合計の年次推移グラフ。年度別の金額はグラフ下の表示する年度で選択して確認できます」とする。
  - クリック・タップ・ドラッグ・ホバーの操作は変えない。
- **数値表示欄**
  - 既存どおり `aria-live="polite"` で、内容が変わったときだけ更新する。
  - 年度選択欄で選ぶと「2040年 固定中」と各項目名・金額が読み上げられ、年度と金額の対応が文字情報で伝わる。
- **ツールチップ**
  - `role="tooltip"` とし、`aria-hidden` は付けない（UI実装ガイドライン 9）。
  - マウス操作専用の一時表示で、同じ情報は年度選択欄と数値表示欄から得られる（FR-021）。

### Rationale

- 標準の `select` は、値なし（プレースホルダー）を自然に表せる。キーボード、デスクトップとスマートフォンの読み上げソフトのいずれでも、追加の ARIA なしで操作できる。
- 年度・金額は DOM の文字（年度選択欄の選択肢と数値表示欄）にあり、Canvas の描画に頼らずに取得できる。
- `visually-hidden-focusable` で、マウス・タッチの利用者の画面を変えずに追加できる。キーボード利用者には、フォーカスしたときに表示とフォーカスリングが見える（2.4.7）。
- `role="img"` に `tabindex` を付けた現状の「操作できない画像にフォーカスが当たる」問題（4.1.2）も解消する。

### 既存の動作からの変更点（要確認として記録）

- **キー操作の場所**：キー操作のフォーカス先が Canvas から年度選択欄に移る。←/→/Home/End で年度を選べることは変わらない。Tab の順は「表示項目チェックボックス → 年度選択欄 → 以降」となる。
- **見た目の変化**：年度選択欄はキーボードでフォーカスした間だけ表示され、その間は数値表示欄が年度選択欄の高さ分だけ下がる。

### Alternatives considered

- `role="slider"`／`role="spinbutton"`：上記の評価のとおり不採用。
- 年度選択欄を常に表示する：確実だが、要件にないUIが増え、画面が縦に伸びる。年度の見出しとも重複する。
- 年度選択欄を完全に非表示（`visually-hidden`）にする：見える利用者がキーボードで操作すると、フォーカスが見えなくなるため不採用（2.4.7）。
- Canvas を `role="application"` にする：支援技術の通常操作を奪うため不採用。

## R7. 凡例の削除とチェックボックスの色表示（FR-010〜012）

- **Decision**:
  - JavaScript が生成する各チェックボックスのラベルに、数値表示欄と同じ線形の色マーカーを追加する。マーカーは装飾なので `aria-hidden="true"` とし、項目名の文字で識別できるようにする。
  - チェックを外してもマーカーは残す。
  - ビューの凡例要素（`data-life-plan-chart-legend`）と、それを描く処理を削除する。
- **Rationale**: 色の識別をチェックボックスに集約すると、項目名の重複が3か所から2か所になる（SC-004）。系列色と白背景のコントラストは次のとおりで、いずれも 3:1 以上を満たす（FR-012）。

  | 系列 | 色 | 白背景とのコントラスト比（概算） |
  | --- | --- | --- |
  | 収入合計 | `#2f8f5b` | 約4.0 |
  | 支出合計 | `#d96045` | 約3.7 |
  | 貯蓄合計（0%運用） | `#2f67b1` | 約5.6 |
  | 貯蓄合計（想定年利運用） | `#6f5fc7` | 約5.1 |

- **Alternatives considered**: チェックを外した項目のマーカーを薄くする案は、Clarifications Q8(c) と、色に頼った状態表示を避ける方針から不採用。

## R8. 数値表示欄の視覚整理（FR-016〜018）

- **Decision**:
  - 見出し行は「2040年」を本文より大きめの太字にし、その横に「固定中」の小さなラベルを付ける。
  - 各行は「色マーカー＋項目名（小さめ・通常の太さ）」と「金額（本文サイズ・太字・等幅数字）」の2要素とする。「万円」は金額の直後に小さめで付ける。
  - 既存の2列（PC）・1列（狭い幅）のグリッドと、金額だけを次の行に右寄せで回す折り返しを維持する。
  - 未選択時は「年度が選択されていません」とする。表示項目がない場合の「表示項目が選択されていません。」は維持する。
- **Rationale**: 表示する情報は変えず、強弱と配置だけを整理する（REQ-05）。既存のトークン（`--ui-font-size-small`、`--ui-font-size-body`）の範囲で表現でき、新しいトークンは不要。
- **Alternatives considered**: 表形式（table）にする案は、狭い幅で横にはみ出しやすいため不採用。

## R9. 描画の更新頻度と応答時間（SC-002）

- **Decision**: ホバー年度が変わったときだけ Canvas を再描画し、ツールチップを更新する。同じ年度の範囲内のカーソル移動では何もしない。待ち時間やアニメーションは入れない。
- **Rationale**: 年度は最大約85件で、1回の再描画は軽い。年度が変わったときだけ描くことで、カーソル移動中の負荷を抑えつつ、即時に表示できる。`requestAnimationFrame` による間引きは不要と判断した。

## R10. 検証方法

- **Decision**:
  - C# の変更はないため、既存の `dotnet build` / `dotnet test` で回帰がないことを確認する。
  - 画面の挙動は、前回と同じく Edge headless のハーネス（実 CSS・JS を読み込み、合成 PointerEvent・KeyboardEvent を送る）と、各画面幅のスクリーンショットで確認する。
  - 実機のスマートフォンとスクリーンリーダーでの確認は、手動確認の項目として [quickstart.md](quickstart.md) に残す。
- **Rationale**: リポジトリに JavaScript のテスト基盤はなく、導入は要件外（憲章 原則 IV）。憲章 原則 III（計算ロジックのテスト）は、今回は計算ロジックの変更がないため対象外。
