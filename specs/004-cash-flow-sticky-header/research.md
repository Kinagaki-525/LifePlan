# Research: スマートフォン版キャッシュフロー表の年度ヘッダー固定と年齢表示

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-10-12

調査は `004-cash-flow-sticky-header`（`develop` の `cfb8f53` から分岐）で行った。アプリを起動し、Chromium（Playwright、スマートフォンの画面とタッチを模擬）で結果画面を計測した。入力は夫 30 歳・妻 26 歳、その他は初期値。

## R0. 現状の計測結果

| 項目 | 幅 390px | 根拠 |
| --- | --- | --- |
| `.life-plan-cash-flow` の `overflow-x` / `overflow-y`（計算後） | `auto` / `auto` | `overflow-x: auto` だけを指定しても、`overflow-y` は `visible` のままにならず `auto` になる（CSS Overflow の仕様） |
| 表の枠の内側の幅 / 表の横幅 | 298px / 6,938px | 年度 75 列＋「区分」「項目」 |
| 表の高さ / 見出し行の高さ | 1,105px / 40px | 子ども 0 人 |
| 表の枠の祖先で `overflow`・`contain` が指定された要素 | なし | ページの縦スクロールに対する `position: sticky` を妨げる祖先はない |
| ページ全体の横幅 | 390px | ページの横スクロールなし |

- 表の枠（`.life-plan-cash-flow`）は縦方向にもスクロールの基準（スクロールコンテナ）になっている。そのため、`thead th` に `position: sticky; top: 0` を加えても、基準は表の枠になり、表の枠自体は縦にスクロールしないので、ページを縦にスクロールしても止まらない（Issue の懸念どおり）。
- Bootstrap の Reboot が `:root { scroll-behavior: smooth }` を指定している。自動操作でページをスクロールするときは `behavior: 'instant'` を指定しないと、計測時点でスクロールが終わっていない（quickstart の注意事項）。

## R1. ヘッダー固定の方式（主要な判断）

**Decision**: **案A：固定用の見出し（複製）を表の枠の外に置き、`position: sticky` で縦に固定し、横位置だけを JavaScript で表の枠に合わせる。** 既存の表の枠・表・横スクロール・固定列の CSS には手を入れない。

**比較**：

| 案 | 仕組み | 縦の動き | 横の動き・列の一致 | 既存の横スクロールへの影響 | 変更範囲・保守性 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. 複製の見出しを sticky で固定し、横位置を同期** | 表の枠の直前に、見出し行だけを複製した表を置く。複製の入れ物を `position: sticky; top: 0` にし、表の枠の `scroll` イベントで複製の `scrollLeft` を合わせる | ブラウザが描画と同時に処理する（JavaScript の遅れがない） | 表の枠の横スクロール中に、複製の追従が最大 1 フレーム遅れうる（iPhone の慣性スクロール中）。列幅は元の見出しの実測値を複製に設定してそろえる | **なし**（表の枠・表の CSS と構造を変えない） | JS 1 ファイル（約 100 行の見込み）、CSS 少量、View に入れ物 1 つ | **採用** |
| B. 元の見出しを JavaScript で縦にずらす | ページの `scroll` ごとに、元の `thead` に `transform: translateY(…)` を設定し、止まって見せる | ページの縦スクロール中に、毎回 JavaScript の計算が 1 フレーム遅れる。iPhone の慣性スクロールでは見出しが縦に揺れることが広く報告されている | 見出しは表の中にあるため、横は常に一致する | 小（`thead` に変形を加える。固定列の重なり順 `z-index` の調整が要る） | JS 少量 | 不採用：主な操作である縦スクロールで揺れが出る |
| C. 表の枠の中で縦スクロールさせる | 表の枠に高さの上限を設け、枠の中で縦横にスクロールする。`thead` に `position: sticky; top: 0` | ブラウザが処理 | 一致 | 中（枠の高さが変わる） | CSS のみ | **不採用**：Clarifications でスクロールの二重化を採らないと決定（FR-009） |
| D. 表の枠のスクロール方式を変える（`overflow-x: clip` など） | 表の枠をスクロールコンテナでなくし、`thead` の sticky をページ基準にする | ブラウザが処理 | — | **大**：`clip` では横スクロールできなくなる。ページ全体の横スクロールに変えると正本 6.2 と FR-018 に反する | — | 不採用：横スクロールを壊す |
| E. スクロール駆動アニメーション（CSS `animation-timeline`）で見出しを縦にずらす | 案B の縦の移動量を CSS だけで、ページのスクロール位置に連動させる | ブラウザが処理 | 一致 | 小 | CSS のみ。ただし移動量の範囲指定が複雑 | 不採用：iOS は Safari 26 以降のみ対応で、iOS 18 以前では固定されない。表の高さに応じた範囲の指定が難しく、保守性が低い |
| F. `position: fixed` の複製を表示・非表示する | 案A の複製を `fixed` にし、表が画面上端を通過する間だけ JavaScript で表示する | 表示の切り替えと解除の位置を JavaScript で決める | 案A と同じ | なし | 案A より JavaScript が多い（固定・解除の判定、押し出しの再現） | 不採用：案A は固定・解除・表の終端での押し出しをブラウザに任せられる |

**Rationale**:

- 最優先の「既存の横スクロールと固定列を壊さない」（FR-020）を、**表の枠・表の構造と CSS を一切変えない**ことで満たせるのは、案A・案F だけである。案A のほうが JavaScript が少ない。
- 縦の固定・解除・表の終端での押し出し（User Story 2 の①〜⑤）を、ブラウザの `position: sticky` に任せられる。固定用の見出しの入れ物を「固定用の見出し＋表の枠」だけを囲む要素の中に置けば、固定の範囲が表の先頭から終端までに限られ、単位の注記やグラフの上には出ない（FR-011）。
- JavaScript の遅れが出うるのは、**固定中に表を横へ慣性スクロールしている間の、見出しの横位置だけ**である。表を読む主な操作である縦スクロールでは遅れが出ない（案B は逆）。
- 試作（R0 と同じ条件、幅 320 / 390 / 1280px、横位置 3 通り × 縦位置 4 通り）で、固定・解除と表の終端での押し出しが期待どおりに動き、見出しと金額の列の左端・幅の差は最大 0.5px（小数点以下の端数）、ページの横幅は画面幅を超えなかった。

**Alternatives considered**: 上表の B〜F。

## R2. 複製の見出しの扱い（操作・読み上げ）

**Decision**:

- 複製は JavaScript で元の `thead` から作る（`cloneNode`）。サーバー側（Razor）では出力しない。
- 複製の入れ物に `aria-hidden="true"` と `inert` を付け、支援技術とキーボードの対象から外す（FR-025）。読み上げとフォーカスは元の表（`thead` を含む）のまま。
- 複製の入れ物は `pointer-events: none` にする。見出しの上でのタッチ・スワイプ・ホイールは、下にある表の枠（固定前は元の見出し、固定中は表の行）に届くので、**見出しの位置でスワイプしても表の枠がそのまま横スクロールする**。同期は表の枠→複製の一方向だけになる。
- 複製の入れ物は `overflow: hidden` とし、横スクロールバーを持たない。
- `id` 属性を持つ要素が複製に含まれる場合は、複製側の `id` を取り除く（現状の `thead` に `id` はないが、将来の重複を防ぐ）。

**Rationale**:

- JavaScript が動かない環境では複製が作られず、表は修正前と同じになる（SC-015）。サーバーで出力すると、JavaScript が動かないときに二重の見出しが見えてしまう。
- 双方向の同期（複製側もスクロール可能にする）は、表の枠の慣性スクロール中に複製側から値を書き戻して、慣性を止めてしまう危険がある。`pointer-events: none` なら同期を一方向にでき、既存の横スクロールの操作（FR-020：スワイプ、トラックパッド、横スクロールバー、キーボード）はすべて表の枠のまま変わらない。

**Alternatives considered**: 双方向同期（上記の危険で不採用）。複製をサーバーで出力（JavaScript が動かないときの二重表示で不採用）。

## R3. 列幅と位置の一致

**Decision**:

- 複製の表は元の表と同じクラス（`life-plan-cash-flow__table`）を持つ。固定列（「項目」の `position: sticky; left`、スマートフォン幅での「区分」の非表示）は、既存の CSS がそのまま複製にも効く。
- 列幅は、元の見出しの各セルの実測幅（`getBoundingClientRect().width`）を複製の対応するセルの `width`・`min-width`・`max-width` に設定し、複製の表の幅も元の表の実測幅にする。
- 元の表の大きさの変化を `ResizeObserver` で監視し、変わったら幅を設定し直す（画面の回転、文字の拡大、結果エリアの表示・非表示、フォントの読み込み完了）。
- 固定前の位置を一致させるため、複製の入れ物の高さを元の `thead` の高さに合わせ、表の枠を同じ高さだけ上へ重ねる（負の `margin-top`）。高さは CSS 変数で JavaScript から渡す。表の枠の枠線・角丸と、複製の入れ物の上側の枠線・角丸をそろえる。
- 試作では固定前の位置が 2〜3px ずれた（表の枠の枠線のぶん）。実装時に上記でそろえ、SC-012 で確認する。

**Rationale**: 年度列は最小幅（6.5rem）で中身が収まるため、通常は全列が同じ幅になるが、文字の拡大や「夫100歳」のような長い表記で列幅が広がる場合にも追従させる。

## R4. 年度ヘッダーの年齢のデータ（C#）

**Decision**:

- `LifePlanResultViewModel.YearHeaders` の型を `IReadOnlyList<string>` から `IReadOnlyList<CashFlowYearHeaderViewModel>` に変える。新しい ViewModel は `Year`（例：`"2026"`）、`HusbandAgeText`（例：`"夫27歳"`、空なら `"夫 -"`）、`WifeAgeText` を持つ。
- 文字列は `LifePlanPageMapper.ToResultViewModel` で、既存の `AnnualCashFlowRow.Year`・`HusbandAge`・`WifeAge` から作る。表本体の年齢行と同じ行データから作るので、列の対応がずれない（FR-002、FR-003）。
- 「年」の接尾辞はスマートフォン幅だけの表示のため、ビューに置き、CSS で出し分ける（PC 幅の `"2026"` を変えない。FR-007）。

**Rationale**:

- 型変換と表示用文字列の生成は Mapper の責務（憲章 原則 II、`.github/copilot-introduction.md` の DTO and Mapper Policy）。年齢の計算はしない。
- `YearHeaders` を使っているのは `Index.cshtml` と既存テスト 1 件だけ（`LifePlanPageMapperResultTests.ToResultViewModel_CreatesYearHeadersFromAnnualRows`）。文字列の一覧を残して別の一覧を足すと、同じ年度の情報が 2 つの一覧に分かれ、ずれる余地が生まれる。

**Alternatives considered**:

- `YearHeaders` を残し、`YearHeaderAges` などを並べて追加する：上記の理由で不採用。
- ビューで `CashFlowRows` の年齢行から拾う：行の検索をビューに持ち込み、ラベル文字列に依存するため不採用。
- JavaScript で表本体の年齢行から作る：JavaScript が動かないと年齢が出ず、表示用データの責務が JS に移るため不採用（憲章 原則 V）。

## R5. 年度ヘッダーの表示と読み上げ

**Decision**:

- 各年度の `th` に、年度・夫の年齢・妻の年齢を別々の `span` で出力する。スマートフォン幅だけで表示する部分（「年」、夫・妻の年齢）は共通のクラスで、PC 幅では `display: none` にする。スマートフォン幅では年齢を改行して 3 段にする（`display: block`）。
- `display: none` の部分は読み上げにも含まれないため、PC 幅の見出しの読み上げは修正前と同じ「2026」。スマートフォン幅では「2026年 夫27歳 妻26歳」（FR-026）。`span` の間にはテンプレート上の改行（空白）を入れ、語が連結しないようにする。
- 見出しは `white-space: nowrap` のまま各段を 1 行にし、列の最小幅（6.5rem）の中に収める。最も長い表記は「夫100歳」（全角 2 文字＋数字 3 桁）。

**Rationale**: 既存の `th scope="col"` と `caption` の構造を変えずに済む（FR-024）。表示の切り替えは CSS だけで行い、JavaScript に依存しない。

## R6. スマートフォン幅だけで有効にする方法

**Decision**: JavaScript は `matchMedia('(max-width: 575.98px)')` が一致するときだけ複製を作り、一致しなくなったら複製を取り除き、表の枠の負の余白などを元に戻す。`change` イベントで画面の回転・幅の変更に追従する。境界の値は既存の CSS（`@media (max-width: 575.98px)`）と同じにする。

**Rationale**: PC 幅では DOM も CSS も修正前と同じになり（View に足す入れ物の要素を除く）、FR-021・SC-014 を満たしやすい。

## R7. iPhone Safari での既知の制約

| 制約 | 影響 | 対応 |
| --- | --- | --- |
| 慣性スクロール中も `scroll` イベントは発生する（iOS 8 以降）が、JavaScript での位置の反映はブラウザの描画より遅れうる | 固定中に横へ慣性スクロールしている間、見出しの年度列が金額の列より一瞬遅れて動く可能性 | 同期は `scroll` イベント内で直接行い、`requestAnimationFrame` で遅らせない。縦の動きには影響しない（R1）。実機で確認する（SC-010） |
| アドレスバー・ツールバーの伸縮で、画面の高さが変わる | `position: sticky; top: 0` は画面の上端を基準にするため、固定位置は変わらない見込み | 実機で隙間・ずれがないか確認する（SC-010） |
| `position: sticky` は祖先に `overflow` の指定があると、その祖先が基準になる | 現状は該当する祖先なし（R0） | 複製の入れ物と表の枠を囲む要素には `overflow` を指定しない。将来の変更で祖先に `overflow` を足さないよう、CSS にコメントを残す |
| `inert` 属性は iOS Safari 15.5 以降で対応 | それより古い端末では、`aria-hidden` と `pointer-events: none` だけが効く | 複製にはフォーカスできる要素がないため、実害はない |
| `ResizeObserver` は iOS Safari 13.4 以降で対応 | それより古い端末では幅を設定し直せない | 初回の設定は行う。古い端末では、回転後に列幅がずれる可能性を許容する（サポート対象外） |
| ピンチで拡大している間は、`position: sticky` の見え方がブラウザごとに異なる | 拡大中の固定位置 | spec の Edge Cases のとおり、ブラウザの挙動に従う。列の対応は崩れない（同じ表の実測値で合わせるため） |

この環境（Chromium のみ）では WebKit の挙動を確認できないため、実機確認（SC-010）は必須とする。

## R8. 実機以外の確認の手段（SC-011〜SC-017）

**Decision**:

| SC | 手段 | 実行場所 |
| --- | --- | --- |
| SC-011 | xUnit：`LifePlanPageMapperResultTests` に、年度ヘッダーの年度・年齢・空の年度（夫が年上・妻が年上）のテストを追加。既存の `YearHeaders` のテストは新しい型に合わせて更新 | `dotnet test LifePlan.slnx -m:1` |
| SC-012 | Playwright（Node.js）＋ Chromium で、`isMobile`・`hasTouch` を有効にした幅 320 / 375 / 390 / 430px と、通常の 1280px で結果画面を表示し、横位置 3 通り × 縦位置 5 通りで数値を計測する | 検証用スクリプト（スクラッチ。リポジトリに含めない） |
| SC-013 | 同じ検証用スクリプトを、修正前（`develop` の `cfb8f53`）と修正後の両方で実行し、横スクロールできる量・各列の幅・固定列の位置を比べる。横スクロールは、タッチのスワイプ（CDP の `Input.dispatchTouchEvent`）、ホイール（`page.mouse.wheel`）、表の枠にフォーカスしての矢印キーの 3 通りで行う | 同上 |
| SC-014 | 1280px で修正前後のスクリーンショット（表の枠の範囲）を撮り、画素単位で比べる | 同上 |
| SC-015 | Playwright の `javaScriptEnabled: false` で、表の全セルの文字と横スクロール・固定列を確認する | 同上 |
| SC-016 | Playwright の `ariaSnapshot()` で、年度の見出しが 1 回だけ現れること、複製が現れないことを確認する。金額セルと見出しの関連は、表の構造（`th scope`）が修正前と同じであることで確認する | 同上 |
| SC-017 | ルートの文字の大きさを 200% にした状態（`document.documentElement.style.fontSize`）と幅 320px で、見出しの各 `span` の `scrollWidth` がセルの幅以下であることを確認する | 同上 |

**Rationale**:

- この環境には Chromium と Playwright が用意されており、幅 320px などの狭い画面と、タッチ・スマートフォンの模擬ができる（003 で使った Edge headless は幅 500px 未満にできず `iframe` で回避していた）。
- 検証用スクリプトは、001〜003 と同じく一時フォルダに置き、リポジトリに含めない（新しい依存パッケージを追加しない。憲章 原則 IV）。手元の Windows 環境では、Playwright がない場合、ブラウザの開発者ツールのデバイスモードで quickstart の手動確認を行う。
- WebKit の挙動、慣性スクロール、アドレスバーの伸縮は、Chromium では確認できない。SC-010 の実機確認で補う。

**Alternatives considered**: Playwright の WebKit（この環境では導入不可。ブラウザの追加導入は行わない方針）。JavaScript の単体テスト基盤の追加（新しい依存パッケージになるため不採用）。
