# 変更レビュー

実装差分と関連テストを確認し、修正が必要な問題と検証の不足を日本語で報告する。

## 対象と前提

- ユーザーが指定した対象を優先する。指定がなければ、追跡済みファイルの staged / unstaged 両方と未追跡ファイルを対象にする。
- 最初に対象、比較元、変更ファイルを明記する。ブランチの比較元を `main` などと決めつけない。特定できなければ比較元を確認し、独立して確認できる箇所は先に読む。
- 指定ブランチは比較元との merge-base から HEAD、指定コミットはそのコミットの親から当該コミットを基本とする。別の比較方法が指定されていれば従う。未コミット変更は別枠として扱う。
- 提供された差分だけをレビューする場合は、その範囲を明示する。例示コードを実在するリポジトリのファイルとして扱わない。
- ソース、テスト、設定、仕様書を編集しない。修正案と追加テスト案は報告する。

## 進め方

1. リポジトリの作業ルールと対象機能の仕様を読む。LifePlan では [references/lifeplan.md](references/lifeplan.md) を読み、そこから対象に関係する正本を参照する。他のリポジトリでは、そのリポジトリのルールを使う。
2. 差分を確認する。Git が使える場合は `git status --short`、`git diff --cached`、`git diff`、`git ls-files --others --exclude-standard` などを使い、未追跡ファイルは個別に読む。ユーザーの作業ツリーを変更しない。
3. [references/checklist.md](references/checklist.md) を使い、変更箇所の呼び出し元、受け渡す型、関連テストまで追う。変更の影響に応じて観点を選ぶ。
4. テストの存在だけで判断せず、期待値、境界条件、失敗時の振る舞いを確認する。実装から同じ計算式で期待値を作るテストや、実装の文言だけを固定するテストは、有効な検証かを吟味する。
5. 呼び出し元から渡されたビルド・テスト結果を確認する。独立したレビューエージェントはビルド・テストを実行せず、必要なコマンドを呼び出し元に伝える。スキルを主会話で使う場合は、作業ルールと権限の範囲で実行してよい。
6. 問題を重要度順にまとめ、不足するテストと未確認範囲を続ける。

## 指摘の基準

- 変更に起因する問題を中心に、具体的なコード・仕様・再現条件から説明する。既存の問題を挙げる必要がある場合は、今回の変更で生じた問題と区別する。
- 確認済みの不具合と、追加の確認が必要な懸念を分ける。仕様が不明な挙動を断定しない。
- テスト不足は「どの条件を、どの期待値で確認すべきか」を示す。カバレッジ率やテスト本数だけで合否を決めない。
- 好みのスタイル変更や無関係なリファクタを指摘に混ぜない。問題が見つからなければ、その旨を明記する。
- ビルド・テストの実行結果、静的なコード確認、環境由来の警告を区別する。未実行・実行不能を成功と記載しない。

## 出力

最初にレビュー対象と比較方法を1〜2行で示し、以下の順に報告する。

1. **指摘**：重要度、短い題名、ファイル・行、発生条件、影響、根拠、最小限の修正方針。実在ファイルは参照可能なリンクを使う。提供差分は「提供差分のファイル名・行」として示す。
2. **不足するテスト**：対象、入力・条件、期待結果、単体／結合／UIなどの検証方法。
3. **検証結果・未確認範囲**：実行者、対象の版・状態、コマンド、成功／失敗／未実行、テスト件数が分かればその値、警告と制約。

重要度は次を基準とする。

- **重大**：広範囲で機能が利用できない、データ破損や重大な情報露出につながる。
- **高**：一般的な利用条件で誤結果や主要機能の失敗が生じる。
- **中**：特定の入力や失敗条件で誤動作する。
- **低**：影響が小さいが、具体的に改善が必要な問題。

指摘がない場合も、検証できていない範囲や不足するテストがあれば記載する。
